## ۱. دیتابیس

**نقش‌ها:** کاربر فعلی docker (`madar`) سوپریوزر است و سوپریوزر RLS را دور می‌زند، پس:
- `DATABASE_URL`: مالک، فقط برای مایگریشن و seed.
- `APP_DATABASE_URL`: نقش جدید `madar_app` با `NOBYPASSRLS` که مالک جدول‌ها نیست. API و تست‌ها با این نقش وصل می‌شوند.
- نقش جدای `madar_auth` (ADR 0002) را فعلاً نمی‌سازیم. `madar_app` به جدول‌های Better Auth دسترسی دارد که جدول‌های صفحه کنترل‌اند و RLS ندارند. این تغییر در ADR 0002 ثبت می‌شود.

**جدول‌ها** (Drizzle + مایگریشن SQL دستی برای RLS، تابع‌ها و grant ها):

| صفحه | جدول | نکته |
|---|---|---|
| کنترل | `tenants` | `slug` یکتا، `status` (active/read_only/locked)، `timezone`، `settings` |
| کنترل | `users`، `sessions`، `accounts`، `verifications`، `two_factors` | اسکیمای Better Auth + `username`، `must_change_password`، `phone` و در session فیلد `active_tenant_id` |
| داده | `members` | `user_id`، `display_name`، `title`، `manager_id`، `status` |
| داده | `departments` | `parent_id`، `head_member_id`، `template_key`، `oversight` (jsonb)، `archived_at` |
| داده | `department_memberships` | `dept_role` (head/manager/member/viewer)، `is_primary` |
| داده | `roles`، `role_grants`، `member_roles` | نقش‌های سیستمی هنگام ساخت شرکت ساخته می‌شوند |
| داده | `audit_logs` | `UPDATE/DELETE/TRUNCATE` از `madar_app` گرفته می‌شود؛ زنجیره هش برای هر شرکت |

**تابع‌ها:** `app.current_tenant_id()`، `app.list_memberships(user_id)` (SECURITY DEFINER، خروجی حداقلی برای انتخاب شرکت هنگام ورود)، `app.append_audit(...)` (درج با advisory lock و محاسبه هش).

**کد:** `withTenant(tenantId, memberId, fn)` و `withPlatform(fn)` در `packages/db`. قاعده lint: import مستقیم کلاینت خام خارج از `packages/db` ممنوع.

## ۲. API

**Better Auth داخل NestJS** روی `/api/auth/*`، با adapter Drizzle و این plugin ها:
- `username`: ورود با نام کاربری.
- `twoFactor`: TOTP و کدهای پشتیبان.
- `customSession`: افزودن `activeTenantId` و وضعیت‌ها.
- ثبت‌نام عمومی Better Auth خاموش است. حساب‌ها فقط سمت سرور ساخته می‌شوند: ثبت شرکت یا ادمین.
- Better Auth برای کاربر ایمیل لازم دارد. برای حساب‌های بدون ایمیل یک آدرس جایگزین غیرقابل‌ارسال (`<id>@users.madar.invalid`) ذخیره می‌شود و هیچ‌جا نمایش داده نمی‌شود.

**Guard ها، به ترتیب:**
1. `SessionGuard`: نشست معتبر.
2. `TenantGuard`: عضویت فعال در شرکت فعال، شرکت قفل نیست، و ساخت context در AsyncLocalStorage.
3. `SecurityGateGuard`: اگر تغییر رمز یا فعال‌سازی 2FA لازم است، فقط همان مسیرها باز است.
4. `PermissionGuard`: با دکوریتور `@RequirePermission('member.create')`.

**موتور مجوز v1** در `packages/shared/permissions`:
- `PERMISSIONS`، نقش‌های سیستمی و grant هایشان، و تابع `can(actor, permission, resource)`.
- `scopeFilter` در `packages/db` برای فهرست‌ها.
- دپارتمان ناظر (ADR 0005) اینجا اعمال می‌شود.

**Endpoint ها** (قرارداد Zod در `packages/shared/contracts`، اعتبارسنجی با یک ZodPipe کوچک خودمان، بدون کتابخانه اضافه):

| مسیر | کار |
|---|---|
| `POST /api/tenants` | ثبت شرکت + مالک (با محدودیت نرخ و در تولید کد ثبت‌نام) |
| `/api/auth/*` | ورود، خروج، تغییر رمز، 2FA (Better Auth) |
| `GET /api/me` · `POST /api/me/active-tenant` | کاربر، عضویت، شرکت، مجوزها، کارهای امنیتی باقی‌مانده |
| `GET/POST/PATCH /api/departments` · `PUT /api/departments/:id/oversight` | درخت دپارتمان‌ها، ساخت، ویرایش، بایگانی، تنظیم ناظر (فقط مالک) |
| `GET /api/org-chart` | چارت بر اساس `manager_id` |
| `GET/POST/PATCH /api/members` | فهرست (با فیلتر دسترسی)، ساخت حساب، ویرایش نقش و دپارتمان و مدیر |
| `POST /api/members/:id/reset-password` · `reset-2fa` · `suspend` · `activate` | همه در AuditLog ثبت می‌شوند |
| `GET /api/audit-logs` | فقط مالک و ادمین |

**ثبت در AuditLog:** تغییر نقش، تغییر grant، تغییر عضویت دپارتمان، تغییر ناظر، ساخت، تعلیق یا فعال‌سازی عضو، بازنشانی رمز یا 2FA، ثبت شرکت.

## ۳. وب (موبایل‌اول، راست‌به‌چپ، از کامپوننت‌های دیزاین‌سیستم)

| صفحه | توضیح |
|---|---|
| `/signup` | ثبت شرکت: نام شرکت، شناسه، نام مدیر، نام کاربری، رمز |
| `/login` → `/login/2fa` | ورود و کد شش‌رقمی، با گزینه کد پشتیبان |
| `/select-tenant` | فقط اگر کاربر عضو چند شرکت باشد |
| `/change-password` | اجباری در ورود اول |
| `/setup-2fa` | QR کد (تولید داخلی با کتابخانه `qrcode`) و کدهای پشتیبان؛ اجباری برای مالک و ادمین |
| پوسته اپ | سایدبار و ناوبری پایین، صفحه «امروز» موقت |
| `/settings/departments` | درخت دپارتمان‌ها، افزودن و ویرایش، مدیر، سوییچ ناظر |
| `/org-chart` | چارت قابل جمع‌شدن، روی موبایل عمودی |
| `/settings/members` | جست‌وجو، افزودن عضو (پیشنهاد نام کاربری، رمز موقت فقط یک‌بار با دکمه کپی)، ویرایش، بازنشانی، تعلیق |
| `/settings/audit` | فهرست رویدادهای ممیزی با تاریخ شمسی |

`proxy.ts` در Next 16 فقط وجود کوکی نشست را چک می‌کند و به `/login` می‌فرستد. امنیت واقعی در API است.

## ۴. تست‌ها

- **db:** تست جداسازی برای هر جدول (شرکت الف داده شرکت ب را نه می‌خواند، نه تغییر می‌دهد، نه با `tenant_id` او درج می‌کند)، تست متا روی `pg_catalog`، تست فقط‌افزودنی بودن AuditLog و درستی زنجیره هش.
- **api:**
  - واحد: موتور مجوز.
  - یکپارچه روی دیتابیس واقعی: ثبت شرکت، ورود، 2FA اجباری، ساخت عضو، رد دسترسی بین‌شرکتی (404)، ثبت AuditLog هنگام تغییر نقش، دیدپذیری دپارتمان و ناظر.
- **e2e:** ثبت شرکت → فعال‌سازی 2FA (کد TOTP در خود تست ساخته می‌شود) → ساخت دپارتمان → ساخت عضو → خروج → ورود عضو → تغییر رمز اجباری → عضو فقط دپارتمان خودش را می‌بیند. در هر دو عرض ۳۶۰ و ۱۴۴۰.
- بررسی بصری صفحه‌ها در موبایل و دسکتاپ، روشن و تیره.

## ۵. داده نمونه

شرکت فرضی **«زرین‌مدار»** (طلای آنلاین)، طبق `docs/pilot-assumptions.md`:

| دپارتمان | نفرات | ناظر |
|---|---|---|
| مدیریت ارشد | ۲ | کار، پروژه، هدف، شاخص، تایید |
| فنی | ۷ | — |
| مارکتینگ | ۴ | — |
| پشتیبانی | ۴ | — |
| منابع انسانی | ۳ | پرسنل، مرخصی، چارت |

- ۲۰ نام فارسی و خط گزارش‌دهی کامل.
- مالک: مدیرعامل. یک ادمین سیستم از منابع انسانی.
- رمز همه حساب‌های نمونه از `SEED_PASSWORD` در `.env` (فقط توسعه). مالک در اولین ورود باید 2FA را فعال کند.
