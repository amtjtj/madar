# پلن فاز ۲الف، قدم ۱۵الف — چت (کانال پروژه، کانال دپارتمان، خصوصی و گروه)

> وضعیت: **در انتظار تایید** · تاریخ: ۲۸ مهر ۱۴۰۵
> مرجع:
> - `docs/feedback/1405-07-27-team-review.md` بخش ۱۰
> - `docs/architecture.md` بخش ۱۰ (۱۰.۲ جدول‌ها، ۱۰.۳ رویدادها، ۱۰.۵ دسترسی، ۱۰.۶ بند ۲ و ۸، ۱۰.۸ پاسخ‌های ۳ و ۵)
> - ADR های 0010، 0011، 0012، 0019، 0021
>
> **درخواست مالک محصول (۲۸ مهر):** «چت داخل پروژه، چت کلی، جای وصل شدن AI». این سه با هم بیش از یک جلسه کار است، پس سه قدم پشت سر هم می‌شوند:
> - **۱۵الف (این پلن):** چت پایه؛ کانال پروژه، کانال دپارتمان، گفت‌وگوی خصوصی و گروه.
> - **۱۵ب:** پیوست، منشن، واکنش، جست‌وجو، تبدیل پیام به کار و سنجاق پیام به‌عنوان شاهد، خروجی چت.
> - **۱۵ج (تازه):** نقطه اتصال AI؛ سرویس `apps/ai`، دروازه AI در API و پنل «دستیار مدار». خلاصه‌اش در انتهای همین سند است و پلن کاملش پیش از شروع ۱۵ج نوشته می‌شود.

## هدف

مریم وارد «گفت‌وگو» می‌شود و کانال پروژه «اپ موبایل ۲٫۳» را بالای فهرست، با ۴ پیام خوانده‌نشده، می‌بیند. این کانال با ساخت پروژه خودکار ساخته شده و اعضایش همان اعضای پروژه‌اند. پیام می‌دهد «نسخه امشب منتشر می‌شود»، و همه اعضای پروژه که آنلاین‌اند همان لحظه پیام را می‌بینند. بقیه، در ساعت کاری، اعلان push می‌گیرند.

کانال «پشتیبانی» برای همه اعضای دپارتمان پشتیبانی است. علی با مریم گفت‌وگوی خصوصی باز می‌کند و یک گروه سه‌نفره «شیفت شب» هم می‌سازد. روی پیام‌ها پاسخ می‌دهد، و پیامی را که اشتباه نوشته تا ۱۵ دقیقه ویرایش یا حذف می‌کند. هر گفت‌وگو را می‌شود بی‌صدا کرد. هیچ مدیر یا ادمینی گفت‌وگوی خصوصی و گروه دیگران را نمی‌بیند.

## محدوده

| داخل این قدم | بیرون از این قدم |
|---|---|
| کانال پروژه: خودکار با ساخت پروژه، اعضا همگام با اعضا و ناظران پروژه | کانال برای ناظران دپارتمانی (پاسخ ۱۰.۸ بند ۵: نه) |
| کانال دپارتمان: خودکار برای هر دپارتمان، اعضا همگام با عضویت دپارتمان | کانال دلخواه عمومی شرکت (مثل «همه») |
| گفت‌وگوی خصوصی دونفره و گروه دلخواه (۳ تا ۵۰ نفر، با نام) | تماس صوتی و تصویری |
| پیام متنی، پاسخ به پیام، ویرایش و حذف تا ۱۵ دقیقه | پیوست، منشن، واکنش، جست‌وجو (قدم ۱۵ب) |
| شمار خوانده‌نشده برای هر گفت‌وگو و کل، «خوانده شد تا اینجا» | رسید خواندن تک‌تک افراد |
| زنده: پیام تازه همان لحظه در گفت‌وگوی باز | نشانگر «در حال نوشتن» و آنلاین بودن |
| push با ساعت سکوت، بی‌صدا کردن هر گفت‌وگو | تبدیل پیام به کار، سنجاق پیام (۱۵ب) |
| از صفحه پروژه: دکمه «گفت‌وگوی پروژه» | خروجی چت برای ادمین (۱۵ب) |

## ۱. قواعد

| موضوع | قاعده |
|---|---|
| **نوع‌ها** | `project`، `department`، `direct`، `group`. دو نوع اول را خود سیستم می‌سازد و کسی نمی‌تواند عضو را دستی در آن‌ها اضافه یا کم کند |
| **همگام‌سازی** | ساخت پروژه یا دپارتمان کانالش را می‌سازد. افزودن یا حذف عضو یا ناظر پروژه، و تغییر عضویت دپارتمان، عضویت کانال را در **همان تراکنش** عوض می‌کند. پروژه یا دپارتمان بایگانی‌شده کانال فقط‌خواندنی دارد. برای پروژه‌ها و دپارتمان‌های موجود، مایگریشن کانال می‌سازد |
| **خصوصی** | یک گفت‌وگوی دونفره بین هر دو نفر (کلید یکتا روی جفت مرتب‌شده). پیام به خود مجاز نیست |
| **گروه** | سازنده نام می‌گذارد و اعضا را انتخاب می‌کند. هر عضو می‌تواند عضو تازه اضافه کند یا خودش خارج شود. نام را سازنده عوض می‌کند |
| **پیام** | متن ساده تا ۴٬۰۰۰ نویسه، با همان رندر امن نامه (`LiteText`: پاراگراف، فهرست، پررنگ). پاسخ به پیامی در همان گفت‌وگو. ویرایش و حذف فقط توسط نویسنده و تا ۱۵ دقیقه. حذف نرم است و به‌صورت «این پیام حذف شد» نمایش داده می‌شود |
| **خوانده‌نشده** | `conversation_members.last_read_message_id`. شناسه‌ها UUIDv7 و به ترتیب زمان‌اند، پس خوانده‌نشده یعنی پیام‌های بعد از آن شناسه که مال خود شخص نیستند |
| **عضو غیرفعال** | از کانال‌ها برداشته می‌شود و پیام‌های قبلی‌اش با نامش می‌مانند |
| **دسترسی** | فقط اعضای همان گفت‌وگو. هیچ نقشی، حتی مالک و ادمین، استثنا نیست (۱۰.۵). شرط SQL در `apps/api/src/chat/access.ts` |
| **حالت فقط‌خواندنی شرکت** | خواندن باز است و نوشتن بسته (گارد فعلی) |

## ۲. مدل داده (مایگریشن `0018_chat`)

| جدول | ستون‌ها | نکته |
|---|---|---|
| `conversations` | `id`، `tenant_id`، `kind`، `project_id?`، `department_id?`، `title?`، `direct_key?`، `created_by?`، `last_message_at`، `archived_at`، `created_at` | یکتا روی `(tenant_id, project_id)` و `(tenant_id, department_id)` و `(tenant_id, direct_key)`. check: هر نوع فقط ستون خودش را دارد |
| `conversation_members` | `conversation_id`، `member_id`، `last_read_message_id`، `muted`، `joined_at`، `left_at` | یکتا روی `(tenant_id, conversation_id, member_id)`. ایندکس `(tenant_id, member_id)` برای فهرست |
| `messages` | `id` (UUIDv7)، `conversation_id`، `author_id`، `body`، `reply_to_id`، `edited_at`، `deleted_at`، `created_at` | ایندکس `(tenant_id, conversation_id, id)` برای صفحه‌بندی (۱۰.۶ بند ۸) |

- **امنیت جدول‌ها:** RLS اجباری و کلید خارجی مرکب. نقش برنامه روی `messages` و `conversations` اجازه DELETE ندارد. ترک گروه نرم است (`left_at`).
- **تست‌ها:** هر سه جدول به fixture و فهرست‌های تست RLS اضافه می‌شوند. کلید مرکب (عضو شرکت دیگر) رد می‌شود.

## ۳. API

| مسیر | توضیح |
|---|---|
| `GET /api/conversations` | گفت‌وگوهای من، به ترتیب آخرین پیام: نوع، عنوان (برای خصوصی، نام طرف مقابل)، آخرین پیام کوتاه‌شده، شمار خوانده‌نشده، بی‌صدا |
| `GET /api/conversations/unread-count` | جمع خوانده‌نشده‌ها (جز بی‌صداها) برای نشان ناوبری |
| `POST /api/conversations/direct` | `{ memberId }`: گفت‌وگوی خصوصی را برمی‌گرداند یا می‌سازد |
| `POST /api/conversations` | گروه تازه `{ title, memberIds }` |
| `GET /api/conversations/:id` | سربرگ: عنوان، نوع، اعضا، پروژه یا دپارتمان مربوط، `can` |
| `PATCH /api/conversations/:id` | نام گروه |
| `POST /api/conversations/:id/members` و `POST /api/conversations/:id/leave` | فقط گروه |
| `GET /api/conversations/:id/messages?before=&after=&limit=` | صفحه‌بندی با شناسه (UUIDv7) |
| `POST /api/conversations/:id/messages` | `{ body, replyToId? }` |
| `PATCH` و `DELETE /api/messages/:id` | ویرایش و حذف، فقط نویسنده، تا ۱۵ دقیقه (`message_edit_window`) |
| `POST /api/conversations/:id/read` | `{ messageId }`: «خوانده شد تا اینجا» (فقط جلو می‌رود) |
| `PUT /api/conversations/:id/mute` | `{ muted }` |

- **کدهای خطا:** `message_edit_window`، `conversation_read_only` (کانال پروژه یا دپارتمان بایگانی‌شده)، `not_group`.
- **محدودیت نرخ:** ۶۰ پیام در دقیقه برای هر نفر.

## ۴. زنده، اعلان و push (ADR تازه 0022)

- **پیام زنده با محتوا، فقط در اتاق گفت‌وگو** (پیشنهاد ۱۰.۶ بند ۲):
  - اتاق `t:{tenant}:c:{conversationId}`. سرور هنگام اتصال، سوکت را به اتاق گفت‌وگوهای شخص می‌برد و هنگام تغییر عضویت جابه‌جا می‌کند.
  - **پیام تازه، ویرایش و حذف:** خود پیام در اتاق فرستاده می‌شود، تا رفت‌وبرگشت لازم نباشد.
  - **بقیه رویدادها:** مثل قبل فقط یک اشاره‌اند (`conversations.changed` به اتاق شخصی، برای فهرست و شمار).
  - این تنها استثنای قاعده «realtime بدون داده» است و در ADR 0022 ثبت می‌شود.
- **push:**
  - رویداد `message.created` برای هر عضو غیربی‌صدا که آنلاین نیست، از راه همان `Notifier` (ساعت سکوت) یک اعلان `chat_message` می‌سازد.
  - برای هر گفت‌وگو یک اعلان باز، تا ده پیام ده اعلان نشوند (یکتا بودن روی گفت‌وگو تا وقتی خوانده نشده).
  - متن push مثل همیشه بدون محتواست: «پیام تازه در گفت‌وگوهایت».
  - **زنگوله:** اعلان چت در زنگوله نمی‌آید (شمار جدا در ناوبری گفت‌وگو دارد) و فقط push و نشان می‌دهد.

| **ناوبری** | دسکتاپ: «گفت‌وگو» در نوار کناری با شمار خوانده‌نشده. **گوشی:** نوار پایین پر است، پس پیشنهاد می‌کنم «گفت‌وگو» جای «اهداف» را در نوار پایین بگیرد. اهداف از تب «اهداف من» در صفحه خانه و از هاب «سازمان» در دسترس می‌ماند (سوال ۱) |
| **صفحه پروژه** | دکمه «گفت‌وگوی پروژه» |
| **دیزاین‌سیستم** | `ChatBubble`، `ConversationRow`، `DayDivider`، کادر نوشتن |

## ۶. تست‌ها

- **واحد:** قرارداد Zod؛ پنجره ۱۵ دقیقه؛ کلید خصوصی؛ گروه‌بندی پیام‌ها بر اساس روز و نویسنده؛ `ChatBubble` (HTML خام تولید نمی‌کند).
- **پایگاه داده:** RLS سه جدول؛ یکتایی کانال پروژه، کانال دپارتمان و گفت‌وگوی خصوصی.
- **یکپارچه (API):**
  - کانال پروژه با ساخت پروژه ساخته می‌شود؛ افزودن و حذف عضو و ناظر پروژه همگام است؛ ناظر دپارتمانی کانال را نمی‌بیند (۴۰۴)؛
  - کانال دپارتمان با عضویت همگام است؛
  - خصوصی یکتاست؛ مالک و ادمین گفت‌وگوی خصوصی دیگران را نمی‌بینند (۴۰۴)؛
  - ویرایش و حذف بعد از ۱۵ دقیقه رد می‌شود؛ پیام دیگری را نمی‌توان ویرایش کرد؛
  - خوانده‌نشده و «خوانده شد تا اینجا»؛ بی‌صدا از شمار کل حذف می‌شود؛
  - push به عضو آفلاین و غیربی‌صدا، نه به نویسنده و بی‌صداها، با ساعت سکوت؛
  - realtime: پیام فقط به اتاق همان گفت‌وگو می‌رود و سوکت عضو برداشته‌شده از اتاق خارج می‌شود؛
  - **شرکت دیگر:** ۴۰۴ برای گفت‌وگو و پیام؛ عضو شرکت دیگر به گروه اضافه نمی‌شود.
- **e2e (۳۶۰ و ۱۴۴۰):**
  - مریم در کانال پروژه پیام می‌دهد و علی (در صفحه دیگر) همان لحظه آن را می‌بیند؛
  - علی پاسخ می‌دهد و پیامش را ویرایش می‌کند؛
  - گفت‌وگوی خصوصی و گروه ساخته می‌شود؛
  - شمار خوانده‌نشده در ناوبری کم و زیاد می‌شود؛
  - کسی که عضو نیست با آدرس مستقیم «پیدا نشد» می‌بیند.
- **بررسی چشمی:** فهرست، گفت‌وگو و ساخت گروه در هر دو عرض و هر دو پوسته.

## ۷. ترتیب کار (هر مرحله یک commit سبز)

1. **shared:** قرارداد چت، پنجره ویرایش، نوع اعلان `chat_message`، کدهای خطا، رشته‌ها؛ با تست.
2. **db:** مایگریشن `0018` (سه جدول، RLS، ایندکس، ساخت کانال برای پروژه‌ها و دپارتمان‌های موجود) و تست‌ها.
3. **API، هسته:** دسترسی، گفت‌وگوها، پیام‌ها، خوانده‌نشده، بی‌صدا، همگام‌سازی با پروژه و دپارتمان و عضو غیرفعال، محدودیت نرخ؛ تست‌ها.
4. **API، زنده و push:** اتاق گفت‌وگو، پیام با محتوا در اتاق، اشاره‌ها، اعلان و push؛ تست‌ها.
5. **UI:** `ChatBubble`، `ConversationRow`، `DayDivider`، کادر نوشتن؛ بخش دیزاین‌سیستم؛ تست.
6. **وب:** `/chat` و `/chat/[id]`، گفت‌وگوی تازه، ناوبری و شمار، دکمه صفحه پروژه، زنده و Optimistic.
7. **پایان:**
   - seed: چند پیام در کانال پروژه و دپارتمان، یک گفت‌وگوی خصوصی و یک گروه «زرین‌مدار»؛
   - e2e؛ ADR 0022 (چت: دسترسی، همگام‌سازی، پیام زنده با محتوا)؛ یادداشت‌های `CLAUDE.md`؛
   - `pnpm check`، e2e کامل، بررسی چشمی؛ بازبینی مستقل؛ پوش.

## سوال‌ها برای مالک محصول

1. **نوار پایین گوشی:** «گفت‌وگو» جای «اهداف» را بگیرد (پیشنهاد من، چون چت پرکاربردترین ابزار روزانه است)، یا مثل نامه یک آیکون کنار زنگوله باشد؟
2. **کانال عمومی شرکت:** یک کانال «همه» برای کل شرکت (فقط مدیران بنویسند، بقیه بخوانند) در همین قدم لازم است؟ پیشنهاد من: بعداً.
3. **ویرایش و حذف:** ۱۵ دقیقه مناسب است؟

## پیش‌نمای قدم ۱۵ج — نقطه اتصال AI (پلن کامل پیش از شروعش)

**هدف:** جایی که مدل هوش مصنوعی داخلی به مدار وصل شود، بدون اینکه داده هیچ شرکتی بیرون برود یا با شرکت دیگری قاطی شود. هر قابلیت AI بعدی (گزارش خودکار، دستیار مدیر، جست‌وجوی هوشمند) روی همین لوله سوار می‌شود.

- **`apps/ai` (Python و FastAPI):**
  - سرویس جدا در Docker، فقط در شبکه داخلی (از اینترنت در دسترس نیست)؛
  - مدل را از یک سرور سازگار با OpenAI صدا می‌زند: vLLM یا Ollama روی سرور GPU خودمان، با `AI_MODEL_URL`؛
  - بدون مدل، حالت «خاموش» دارد و برنامه بدون آن کامل کار می‌کند.
- **دروازه AI در API (`AiModule`):** همه درخواست‌های AI فقط از این راه می‌روند و این‌ها را تضمین می‌کند:
  - شناسه شرکت روی هر درخواست؛ داده فقط از راه `withTenant` و قاعده‌های دسترسی همان شخص خوانده می‌شود؛
  - محدودیت نرخ برای هر نفر و هر شرکت؛
  - ثبت استفاده (بدون متن) برای هزینه؛
  - روشن و خاموش برای هر شرکت توسط مالک.
- **اولین قابلیت‌ها** (کوچک، روی داده‌ای که شخص همین حالا می‌بیند):
  - «خلاصه این گفت‌وگو» در چت؛
  - «پیش‌نویس پاسخ» در نامه؛
  - دکمه دستیار در گزارش هفتگی.
- **پنل «دستیار مدار»:** یک کادر در کنار صفحه. وقتی مدل وصل نیست، می‌گوید «دستیار هنوز روشن نشده».
- **RAG و pgvector:** برای جست‌وجوی هوشمند، با نمایه جدا برای هر شرکت. در قدم بعد از ۱۵ج.
- **سوال‌های مهم آن قدم:**
  - سرور GPU کجا و با چه مشخصاتی؟
  - کدام مدل (مثلاً Qwen 2.5 7B برای شروع)؟
  - تا آماده شدن سرور GPU، یک مدل کوچک روی CPU برای دمو کافی است؟
