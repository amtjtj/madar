# پلن فاز ۳، قدم ۱۷ب: درخواست و تایید (مرخصی، هزینه، درخواست عمومی)

> وضعیت: **پیاده‌سازی شد** (ADR 0028) · تاریخ: ۲ آبان ۱۴۰۵
>
> تفاوت با پلن در پیاده‌سازی:
> - `GET /api/leaves` ساخته نشد؛ تقویم مرخصی را از لایه تازه `leaves` در `GET /api/calendar` می‌خواند.
> - «منابع انسانی» یعنی نقش `hr_manager` یا ناظر `leave`.
> - رهبری فقط وقتی جای تاییدکننده تصمیم می‌گیرد که او دیگر فعال نباشد (نه هر درخواست باز).
> - سقف هزینه در `tenants.settings.approvals` است (نه ستون تازه) و به تومان.
> - رویداد `request.advanced` برای رسیدن به مرحله بعد اضافه شد.
> مرجع:
> - `docs/brief.md` «محدوده MVP»: «هسته: گردش تایید درخواست‌ها (هزینه، مرخصی، محتوا)»؛ گیمیفیکیشن: «روزهای تعطیل و مرخصی استریک را نمی‌شکنند»
> - `docs/architecture.md` بخش ۲ (جدول‌های `approval_requests`، `approval_steps`، `leaves`) و بخش ۳.۲ (`ApprovalFlowDef`)
> - ADR 0005 (اجازه‌ها)، 0009 (AuditLog)، 0011 (رویداد و اعلان)، 0024 (تقویم)، 0027 (مدیر و زنجیره گزارش‌دهی)
> - `docs/pilot-assumptions.md`: منابع انسانی ناظر «مرخصی» است
> - قدم قبل: `docs/plans/phase-3-step-17a.md`
>
> چرا الان: آخرین قطعه هسته MVP که ساخته نشده، همین است. میزیتو آن را دارد (شرط خاموش کردن میزیتو)، و هم «قالب دپارتمان» (فرم‌ها و گردش‌های سفارشی) و هم گیمیفیکیشن (مرخصی استریک را نمی‌شکند) روی آن ساخته می‌شوند.

## هدف

علی از گوشی روی «درخواست تازه» می‌زند، «مرخصی» را انتخاب می‌کند، از ۵ تا ۷ آبان را با تقویم شمسی می‌زند و یک خط توضیح می‌نویسد. مدیرش، مریم، اعلان می‌گیرد و در «کارتابل» با یک لمس تایید می‌کند. علی فوراً می‌بیند تایید شد، و آن سه روز در تقویم تیم با رنگ مرخصی دیده می‌شود. زهرا برای خرید هدست ۱۸ میلیون تومان «درخواست هزینه» با عکس فاکتور ثبت می‌کند. چون مبلغ بالای سقف شرکت است، بعد از مریم به مدیرعامل هم می‌رود. هر تصمیم با نام، زمان و توضیح ثبت می‌شود و قابل پاک کردن نیست.

## محدوده

| داخل این قدم | بیرون از این قدم |
|---|---|
| سه نوع درخواست با فرم ثابت در کد: مرخصی (روزانه یا ساعتی)، هزینه (مبلغ، دسته، پیوست)، عمومی (عنوان و متن) | فرم و گردش سفارشی از UI (با «قالب دپارتمان»، قدم بعد) |
| گردش تایید یک یا دو مرحله‌ای: مدیر درخواست‌کننده، و برای هزینه بالای سقف مدیرعامل | شرط‌های دلخواه (`when`)، تایید موازی، جانشین در غیاب |
| کارتابل: «منتظر من»، «درخواست‌های من»، «تصمیم‌های من» | گزارش و خروجی مالی |
| تایید، رد با دلیل، لغو توسط درخواست‌کننده قبل از تصمیم | ویرایش درخواست بعد از ثبت (لغو و ثبت دوباره) |
| مرخصی تاییدشده در جدول `leaves` و لایه تازه «مرخصی» در تقویم | مانده مرخصی و سهمیه سالانه |
| اعلان و push، به‌روزرسانی زنده، AuditLog | پرداخت یا اتصال به حسابداری |
| تنظیم شرکت: سقف هزینه برای مرحله دوم | |

## ۱. قواعد

| موضوع | قاعده |
|---|---|
| **چه کسی تایید می‌کند** | مرحله ۱: مدیر مستقیم درخواست‌کننده (`members.manager_id`)؛ اگر نداشت، رئیس یا مدیر دپارتمان اصلی‌اش؛ اگر خودش رئیس است، رهبری (`leadsCompany`). مرحله ۲ (فقط هزینه بالای سقف): رهبری. اگر تاییدکننده مرحله ۲ همان مرحله ۱ بود، مرحله ۲ حذف می‌شود |
| **تاییدکننده مشخص** | هنگام ثبت، `approver_member_id` هر مرحله محاسبه و در `snapshot` ذخیره می‌شود. تغییر مدیر بعداً درخواست باز را عوض نمی‌کند، مثل قاعده snapshot معماری. رهبری هر درخواست باز را می‌تواند تصمیم بگیرد (اگر تاییدکننده نبود) |
| **خود را تایید نکن** | هیچ‌کس درخواست خودش را تایید نمی‌کند؛ اگر محاسبه به خود شخص رسید، به مرحله بالاتر (رهبری) می‌رود |
| **چه کسی می‌بیند** | درخواست‌کننده، تاییدکننده‌های همان درخواست، رهبری، و ناظر `approval` (موجود در `OVERSIGHT_RESOURCES`). منابع انسانی ناظر `leave` فقط مرخصی‌ها را می‌بیند. همه با یک شرط SQL (`visibleRequests`) |
| **دسترسی پیوست** | فاکتور هزینه مثل بقیه فایل‌ها از `AttachmentsService` با شاخه تازه `approval_request` و همان شرط دیدن (ADR 0019) |
| **فقط افزودنی** | `approval_steps` فقط درج می‌شود (RLS محدودکننده مثل نامه)؛ وضعیت درخواست فقط با تصمیم یا لغو جلو می‌رود: `pending` → `approved`/`rejected`/`canceled` |
| **ممیزی** | ثبت، تایید، رد و لغو در AuditLog (بدون متن توضیح؛ مبلغ برای هزینه بله) |
| **مرخصی** | در تایید نهایی، یک سطر `leaves` در همان تراکنش ساخته می‌شود. مرخصی روزانه روزهای تعطیل شرکت را نمی‌شمارد. مرخصی هم‌پوشان با مرخصی تاییدشده قبلی رد می‌شود (`leave_overlap`) |
| **گیمیفیکیشن** | فقط داده آماده می‌شود (`leaves`)؛ استریک در قدم خودش. تایید یا رد هیچ امتیازی نمی‌دهد و نمی‌گیرد |
| **ساعت سکوت** | اعلان‌ها از `Notifier` با همان ساعت سکوت |

## ۲. مدل داده (مهاجرت تازه، همه با `tenant_id` و RLS اجباری)

| جدول | ستون‌ها |
|---|---|
| `approval_requests` | `id` (UUIDv7)، `kind` (`leave`/`expense`/`general`)، `requester_id`، `department_id`، `title`، `data jsonb` (فیلدهای فرم، با Zod مشترک)، `amount` (ریال، فقط هزینه، برای سقف و گزارش)، `status`، `current_step`، `snapshot jsonb` (مرحله‌ها و تاییدکننده‌ها)، `created_at`، `decided_at` |
| `approval_steps` | `request_id`، `step_index`، `approver_member_id`، `decision` (`approved`/`rejected`)، `comment`، `decided_at`؛ یکتا روی (درخواست، مرحله)؛ فقط درج |
| `leaves` | `member_id`، `request_id`، `kind` (`daily`/`hourly`)، `starts_on`، `ends_on`، `starts_at?`، `ends_at?`، `created_at` |
| `tenant_settings` (موجود) | `approval_expense_threshold` (ریال، پیش‌فرض ۱۰۰ میلیون ریال) |

کلیدهای خارجی ترکیبی `(tenant_id, x)`، `app.enable_tenant_rls(...)` برای هر سه جدول، و تست جداسازی برای هر کدام.

## ۳. اجازه‌ها

- ثبت: هر عضو فعال، برای خودش.
- تصمیم: فقط تاییدکننده مرحله جاری، یا رهبری؛ هرگز درخواست‌کننده.
- دیدن: `visibleRequests(actor)` بالا. نقش admin (مدیر سیستم) استثنا نیست.
- تنظیم سقف: `tenant.manage`.

## ۴. API

| مسیر | توضیح |
|---|---|
| `POST /api/requests` | `{ kind, title?, data, uploadIds? }`؛ Zod بر اساس `kind`؛ تاییدکننده‌ها حساب و snapshot می‌شوند |
| `GET /api/requests?box=pending\|mine\|decided` | کارتابل، صفحه‌بندی با کرسر |
| `GET /api/requests/:id` | جزئیات، مرحله‌ها، پیوست‌ها، `can: { decide, cancel }` |
| `POST /api/requests/:id/decide` | `{ decision, comment? }`؛ رد بدون توضیح پذیرفته نیست (`comment_required`) |
| `POST /api/requests/:id/cancel` | فقط درخواست‌کننده، فقط `pending` |
| `GET /api/leaves?from&to&member?` | برای تقویم (لایه `leave`) با شرط دیدن |
| `PUT /api/settings/approvals` | سقف هزینه |

رویدادها: `request.submitted`، `request.decided`، `request.canceled`؛ اعلان‌های تازه `request_waiting` (به تاییدکننده) و `request_decided` (به درخواست‌کننده)، با رشته‌های `notifications.kinds.*`، `notificationSettings.kinds.*` و `pwa.pushMessages.kinds.*`.

## ۵. صفحه‌ها (موبایل‌اول، RTL)

- **«درخواست‌ها»** (`/requests`): سه زبانه کارتابل با شمارنده «منتظر من». روی موبایل از هاب «سازمان» و کارت «منتظر تایید تو» در خانه (فقط وقتی چیزی هست). روی دسکتاپ در منوی کناری.
- **درخواست تازه**: انتخاب نوع با سه کارت بزرگ، فرم کوتاه. مرخصی: روزانه با `DatePicker` بازه‌ای، یا ساعتی با فهرست ربع‌ساعت فارسی. هزینه: مبلغ با جداکننده فارسی، دسته، پیوست. پیش از ثبت نشان داده می‌شود «به چه کسی می‌رود».
- **جزئیات درخواست**: نوار مرحله‌ها (منتظر، تایید، رد) با نام و زمان، دکمه‌های بزرگ «تایید» و «رد» (رد توضیح می‌خواهد)، و لغو برای درخواست‌کننده. Optimistic با بازگشت در خطا.
- **تقویم**: لایه تازه «مرخصی» با توکن رنگ تازه `--color-layer-leave` در روشن و تیره.
- **تنظیمات شرکت**: سقف هزینه.
- حالت خالی طراحی‌شده برای هر زبانه، اسکلت به‌جای چرخنده.
- اجزای تازه در `@madar/ui`: `RequestRow`، `ApprovalTimeline`، `RequestKindBadge`، `AmountText`، و نمایش در `/design-system`.

## ۶. تست‌ها

- **واحد (shared)**: Zod هر نوع، شمردن روزهای کاری مرخصی با تعطیلی‌ها، محاسبه مرحله‌ها (مدیر، رئیس، رهبری، حذف مرحله تکراری، خود-تایید).
- **یکپارچه (API)**:
  - گردش کامل مرخصی و هزینه (یک و دو مرحله)
  - رد با توضیح؛ لغو؛ تصمیم دوباره رد می‌شود؛ درخواست‌کننده تصمیم نمی‌گیرد
  - snapshot بعد از تغییر مدیر ثابت می‌ماند
  - دید درخواست: همکار نه، ناظر `approval` بله، منابع انسانی فقط مرخصی
  - پیوست فقط برای کسی که درخواست را می‌بیند
  - `leaves` فقط بعد از تایید نهایی؛ هم‌پوشانی رد می‌شود
  - شرکت دیگر هیچ‌چیز نمی‌بیند (درخواست، مرحله، مرخصی، پیوست، اعلان)
  - تست RLS برای هر سه جدول، و این‌که `approval_steps` قابل تغییر یا حذف نیست
- **e2e (۳۶۰ و ۱۴۴۰)**: علی مرخصی می‌خواهد، مریم تایید می‌کند و مرخصی در تقویم تیم دیده می‌شود؛ هزینه بالای سقف به مدیرعامل می‌رسد و رد با دلیل به علی برمی‌گردد.

## ۷. ترتیب کار

1. shared: قراردادها، فرم‌ها، محاسبه مرحله‌ها و روزهای مرخصی، کدهای خطا و رشته‌ها، با تست.
2. db: مهاجرت سه جدول و ستون سقف، RLS، تست جداسازی.
3. API: سرویس درخواست، دید، تصمیم، لغو، پیوست، رویداد، اعلان، audit، با تست.
4. API: لایه مرخصی تقویم و تنظیم سقف.
5. ui و وب: اجزای تازه، کارتابل، فرم، جزئیات، کارت خانه، لایه تقویم، تنظیمات.
6. seed (چند درخواست باز و تاییدشده، یک مرخصی)، e2e، ADR 0028، `CLAUDE.md`، بازبینی، push.

## تصمیم‌های من

| تصمیم | چرا |
|---|---|
| سه نوع ثابت در کد، نه فرم‌ساز | فرم‌ساز بخشی از «قالب دپارتمان» است؛ جدول‌ها (`data jsonb` و `snapshot`) همان شکل معماری‌اند و بعداً فرم سفارشی همین‌جا می‌نشیند |
| تاییدکننده از زنجیره گزارش‌دهی، بعد رئیس دپارتمان | همان قاعده «مدیر کسی» در ADR 0027؛ برای ۲۰۰ نفر بدون تنظیم کار می‌کند |
| مرحله دوم فقط برای هزینه بالای سقف | ساده‌ترین قاعده‌ای که شرکت مالی واقعاً دارد؛ عدد قابل تنظیم است |
| رد بدون توضیح پذیرفته نیست | حس «دیده‌شدن، نه فشار»: درخواست‌کننده باید بداند چرا |
| مرخصی تاییدشده جدول جدا دارد | تقویم، استریک و گزارش منابع انسانی آن را بدون فهمیدن گردش تایید می‌خوانند |
| مبلغ به ریال ذخیره و به تومان نشان داده می‌شود | عدد صحیح بدون اعشار؛ نمایش تومان عادت کاربر ایرانی است |

## سوال برای مالک محصول

1. سقف پیش‌فرض هزینه برای رفتن به مدیرعامل ۱۰ میلیون تومان باشد؟ (پیشنهاد: بله، قابل تغییر در تنظیمات)
2. مرخصی ساعتی هم لازم است یا فقط روزانه؟ (پیشنهاد: هر دو)
3. نوع «محتوا» (تایید طراحی یا پست مارکتینگ) را برای ماژول مارکتینگ در قدم قالب دپارتمان بسازیم؟ (پیشنهاد: بله، آن‌جا به‌عنوان نوع کار با گردش تایید)
