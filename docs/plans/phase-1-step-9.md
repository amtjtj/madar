# پلن فاز ۱، قدم ۹ — استقرار آزمایشی روی ابر ایرانی و آماده‌سازی دمو

> وضعیت: **منتظر تایید** · تاریخ: ۲۷ مهر ۱۴۰۵
> مرجع: `docs/prompts/phase-1-next.md` (قدم ۹)، `docs/architecture.md` (§۸ ریسک‌ها: تحریم رجیستری، Next.js بدون Vercel)، ADR های 0001 (`output: 'standalone'`)، 0002 (نقش‌های دیتابیس)، 0006 (Caddy جلوی web و api روی یک دامنه، worker در کانتینر جدا)، 0011 (worker)، 0012 (Web Push)، `docs/pilot-assumptions.md`

## هدف

مدیرعامل شرکت طلا روی گوشی خودش آدرسی مثل `https://demo.madar.ir` را باز می‌کند، با حسابی که به او داده‌ایم وارد می‌شود، مدار را روی صفحه اصلی نصب می‌کند و داده‌ای واقعی‌نما از شرکت «زرین‌مدار» می‌بیند: اهداف، داشبورد، گزارش هفتگی و اعلان‌های زنده.

کسی که اولین بار سرور راه می‌اندازد، با یک راهنمای قدم‌به‌قدم و سه فرمان، همین را روی یک سرور ابری ایرانی بالا می‌آورد:
- HTTPS خودکار؛
- مایگریشن خودکار؛
- پشتیبان روزانه با آزمایش خودکار بازگردانی؛
- لاگ و وضعیت سلامت، بدون هیچ سرویس خارجی.

برای جلسه دمو یک متن ۱۰ دقیقه‌ای آماده است، از دید سه نقش.

## محدوده

| داخل این قدم | بیرون از این قدم |
|---|---|
| ایمیج تولیدی: یکی برای web (Next standalone) و یکی برای api و worker، با کاربر غیر root | Kubernetes، چند سرور، مقیاس افقی |
| `docker/compose.prod.yml` با Postgres، Redis، Caddy (HTTPS)، api، worker، migrate، backup | CDN و WAF ابری (بعداً روی همان دامنه قابل افزودن است) |
| مایگریشن خودکار پیش از بالا آمدن api و worker | مایگریشن بدون توقف (blue/green) |
| پشتیبان روزانه، نگه‌داری ۷ روزانه و ۴ هفتگی، آزمایش خودکار بازگردانی، کپی اختیاری به ذخیره‌ساز S3 ایرانی | پشتیبان پیوسته (WAL / PITR) |
| ساخت `.env` با رازهای تصادفی؛ بررسی سخت‌گیرانه متغیرها در حالت تولید | مدیریت راز با Vault |
| لاگ ساختاریافته JSON با چرخش، سلامت سرویس‌ها (دیتابیس، Redis، worker)، اسکریپت وضعیت | داشبورد مانیتورینگ و هشدار پیامکی یا پیام‌رسان (سوال ۴) |
| «حالت دمو»: داده «زرین‌مدار» روی سرور، تازه‌سازی شبانه، حساب سه نقش | ثبت‌نام عمومی و پرداخت |
| `docs/deploy.md` و `docs/demo-script.md` | انتقال داده از میزیتو (فاز ۲) |
| تست دود (smoke) روی همان پشته تولیدی در CI: HTTPS، ورود، WebSocket، پشتیبان و بازگردانی | تست بار (load test) |

## ۱. شکل استقرار

```
اینترنت ── 443/80 ──► Caddy ─┬─ /api/* و /api/socket (WebSocket) ──► api   (NestJS)
                              └─ بقیه                               ──► web   (Next standalone)
                                 worker (BullMQ، یادآوری، گزارش هفتگی، push)
                                 postgres 18  ·  redis 8  (فقط شبکه داخلی، بدون پورت باز)
                                 backup (هر شب) ──► ./backups  (+ S3 اختیاری)
                                 migrate (یک‌بار در هر استقرار، قبل از api و worker)
```

- **یک دامنه:** کوکی‌ها first-party می‌مانند و CORS لازم نیست (ADR 0006). Caddy گواهی HTTPS را خودکار می‌گیرد و تمدید می‌کند. اگر گرفتن گواهی خودکار از سرور ایران ممکن نبود، فایل گواهی خودتان را می‌گذارید (سوال ۲).
- **سربرگ‌های امنیتی در Caddy:** HSTS، `X-Content-Type-Options`، `Referrer-Policy`، `Permissions-Policy` و فشرده‌سازی (zstd و gzip). Content-Security-Policy در حالت گزارش (report-only) شروع می‌شود تا چیزی نشکند.
- **ایمیج‌ها:**
  - `madar-api`: یک ایمیج برای api، worker و migrate، با سه فرمان. migrate کامپایل‌شده اجرا می‌شود (بدون `tsx`).
  - `madar-web`: خروجی standalone Next.js، با فونت‌ها و آیکون‌ها.
  - هر دو multi-stage، بر پایه `node:24-alpine`، کاربر غیر root، با healthcheck. برچسب هر ایمیج شناسه commit است تا برگشت به نسخه قبل ممکن باشد.
- **تحریم رجیستری (architecture §۸):** آدرس رجیستری ایمیج پایه (`BASE_REGISTRY`) و رجیستری npm (`NPM_REGISTRY`) در build قابل تنظیم‌اند، تا از آینه‌های داخلی ابرهای ایرانی استفاده شود. ساخت روی خود سرور انجام می‌شود. راه جایگزین بدون اینترنت هم مستند می‌شود: ساخت در جای دیگر، بعد `docker save` و `docker load`.
- **فونت Abar:** در git نیست. پیش از build روی سرور با `pnpm fonts:install` نصب می‌شود و داخل ایمیج web قرار می‌گیرد. بدون آن، Vazirmatn می‌آید.

## ۲. مدل داده

جدول تازه‌ای اضافه نمی‌شود.
- **نقش‌های دیتابیس:** همان نقش‌های فعلی (`madar_owner` برای مایگریشن و پشتیبان، `madar_app` و `madar_worker` با RLS). رمز هر کدام جدا و تصادفی است.
- **ضربان worker:** کلید Redis با انقضای کوتاه (`madar:worker:heartbeat`). شامل هیچ داده‌ای از شرکت‌ها نیست.

## ۳. دسترسی‌ها

بدون تغییر در مجوزها. در حالت تولید:
- ساختن شرکت تازه بدون `TENANT_SIGNUP_CODE` بسته است؛
- seed فقط در حالت دمو اجرا می‌شود؛
- Postgres و Redis پورت بیرونی ندارند.

## ۴. API

| مسیر | تغییر |
|---|---|
| `GET /api/health` | علاوه بر دیتابیس، Redis و ضربان worker را هم گزارش می‌دهد (`ok` / `degraded`). فقط وضعیت است، بدون جزئیات داخلی |

**بررسی متغیرها در تولید** (`NODE_ENV=production`)؛ api و worker در این حالت‌ها بالا نمی‌آیند:
- `AUTH_SECRET` کوتاه یا پیش‌فرض باشد؛
- `AUTH_BASE_URL` با https شروع نشود؛
- `TENANT_SIGNUP_CODE` خالی باشد؛
- رمز پیش‌فرض توسعه در آدرس دیتابیس باشد.

## ۵. حالت دمو

- **`DEMO_MODE=true`** روی سرور دمو یعنی:
  - seed «زرین‌مدار» در تولید اجازه دارد؛
  - رمز همه حساب‌ها `DEMO_PASSWORD` است (تصادفی، نه رمز توسعه).
- **تازه‌سازی:** فرمان `demo:reset` داده را پاک و دوباره seed می‌کند. تاریخ‌های seed نسبت به امروز ساخته می‌شوند، پس داشبورد، کارهای معوق و گزارش‌های هفته‌های قبل همیشه به‌روزند. سرویس backup در حالت دمو هر شب ساعت ۵ صبح تهران همین کار را می‌کند (سوال ۳).
- **حساب‌های دمو:**

| نقش | حساب | چه می‌بیند |
|---|---|---|
| مدیرعامل | `leila.sadeghi` | خانه «شرکت»، اهداف شرکت، گزارش هفتگی و PDF |
| مدیر دپارتمان | `maryam.ahmadi` | «تیم من»، کارهای گیرکرده، گزارش پشتیبانی |
| کارمند | `ali.rezaei` | «امروز من»، هدف‌های من، اعلان زنده |
| مالک (اختیاری) | `reza.karimi` | تنظیمات و اعضا؛ بار اول 2FA می‌خواهد |

## ۶. پشتیبان، بازگردانی و پایش

- **پشتیبان:**
  - سرویس `backup` هر شب ساعت ۳:۳۰ تهران `pg_dump -Fc` می‌گیرد، در `./backups` روی دیسک سرور.
  - نگه‌داری: ۷ نسخه روزانه و ۴ هفتگی.
  - با تنظیم `BACKUP_S3_*`، یک کپی هم به ذخیره‌ساز S3 سازگار ابر ایرانی می‌رود.
- **آزمایش بازگردانی:** بعد از هر پشتیبان، فایل در یک دیتابیس موقت بازگردانی می‌شود. تعداد سطرهای جدول‌های اصلی با دیتابیس اصلی مقایسه می‌شود. نتیجه در `backups/last-check.json` ثبت و در لاگ نوشته می‌شود؛ در صورت شکست، خطا در لاگ و در `status.sh` دیده می‌شود.
- **بازگردانی واقعی:** `scripts/deploy/restore.sh <file>`، با توقف api و worker و تایید دستی. در `docs/deploy.md` تمرین می‌شود.
- **لاگ:**
  - api و worker در تولید لاگ JSON می‌نویسند، با شناسه درخواست. رمز و کوکی و توکن در لاگ نمی‌آیند.
  - Docker هر لاگ را تا ۵ فایل ۱۰ مگابایتی می‌چرخاند.
  - Caddy لاگ دسترسی JSON دارد، بدون query string.
- **وضعیت:** `scripts/deploy/status.sh` نشان می‌دهد:
  - سلامت هر کانتینر و `/api/health`؛
  - آخرین پشتیبان و نتیجه آزمایش آن؛
  - فضای دیسک؛
  - تعداد خطاهای ۲۴ ساعت گذشته.

## ۷. اسکریپت‌های استقرار

| فرمان | کار |
|---|---|
| `scripts/deploy/init-env.sh` | ساخت `.env` تولیدی با رازهای تصادفی، رمز نقش‌های دیتابیس و کلید VAPID؛ دامنه را می‌پرسد. اگر `.env` باشد، چیزی را بازنویسی نمی‌کند |
| `scripts/deploy/deploy.sh` | گرفتن کد، build ایمیج‌ها با برچسب commit، اجرای migrate، بالا آوردن سرویس‌ها، صبر تا سالم شدن، نمایش وضعیت. `--rollback` ایمیج قبلی را برمی‌گرداند |
| `scripts/deploy/status.sh` | وضعیت (بالا) |
| `scripts/deploy/backup-now.sh` و `restore.sh` | پشتیبان دستی و بازگردانی |
| `demo:reset` (داخل کانتینر api) | تازه‌سازی داده دمو؛ بیرون از `DEMO_MODE` رد می‌شود |

## ۸. صفحه‌ها

صفحه تازه‌ای ساخته نمی‌شود. روی ایمیج تولیدی این‌ها بررسی می‌شوند:
- نصب PWA و Web Push روی HTTPS واقعی؛
- WebSocket از پشت Caddy؛
- PDF گزارش.

**عملکرد:** زمان باز شدن خانه روی گوشی (۳۶۰ پیکسل، شبکه کند شبیه‌سازی‌شده) روی build تولیدی اندازه‌گیری و در ADR ثبت می‌شود. هدف بریف زیر ۲ ثانیه است.

## ۹. تست‌ها

- **واحد:**
  - بررسی متغیرهای تولید (رازهای ضعیف، `http`، نبود کد ثبت‌نام رد می‌شوند)؛
  - seed و `demo:reset` بیرون از حالت دمو رد می‌شوند.
- **api:** `/api/health` با worker خاموش `degraded` و با ضربان `ok` است. تست‌های جداسازی موجود بدون تغییر سبز می‌مانند (این قدم داده یا کوئری تازه ندارد).
- **پشته تولیدی (CI و همین‌جا):**
  - ایمیج‌ها ساخته می‌شوند و `compose.prod.yml` با گواهی داخلی Caddy روی `https://localhost` بالا می‌آید؛
  - migrate و seed دمو اجرا می‌شوند؛
  - یک spec کوچک Playwright در ۳۶۰ و ۱۴۴۰ پیکسل روی همان آدرس: ورود سه نقش، خانه هر نقش، پیام زنده از WebSocket، گزارش هفتگی، و `manifest` و `sw.js`؛
  - پشتیبان گرفته و آزمایش بازگردانی پاس می‌شود؛
  - هیچ پورتی جز ۸۰ و ۴۴۳ باز نیست.
- **بازبینی بصری:** گوشی و دسکتاپ، روشن و تیره، روی build تولیدی.

## ۱۰. ترتیب کار (هر مرحله یک commit سبز)

1. بررسی متغیرهای تولید، لاگ JSON با شناسه درخواست، ضربان worker و سلامت گسترش‌یافته، با تست
2. Dockerfile های api و web، `.dockerignore`، migrate کامپایل‌شده، آرگومان رجیستری‌ها
3. `docker/compose.prod.yml` و `docker/Caddyfile` (HTTPS، WebSocket، سربرگ‌ها، فشرده‌سازی، چرخش لاگ)
4. سرویس backup، آزمایش بازگردانی، کپی S3 اختیاری، `restore.sh`
5. اسکریپت‌های `init-env.sh`، `deploy.sh`، `status.sh`
6. حالت دمو: `DEMO_MODE`، `DEMO_PASSWORD`، `demo:reset`، تازه‌سازی شبانه
7. تست دود پشته تولیدی (اسکریپت محلی و job تازه در CI) و اندازه‌گیری عملکرد
8. `docs/deploy.md`، `docs/demo-script.md`، ADR 0016، دستورهای CLAUDE.md و بستن قدم

اندازه: این قدم تقریباً همه‌اش زیرساخت است و کد محصول را کم تغییر می‌دهد، پس در یک جلسه جا می‌شود. اگر تست پشته در CI طول کشید، مرحله ۷ می‌تواند جدا شود.

| موضوع | تصمیم |
|---|---|
| سرور | یک ماشین مجازی معمولی (Ubuntu 24.04، Docker)، مستقل از ارائه‌دهنده. پیشنهاد برای دمو و پایلوت ۲۰۰ نفره: ۴ هسته، ۸ گیگ رم، ۸۰ گیگ SSD |
| reverse proxy | Caddy (طبق ADR 0006): HTTPS خودکار و تنظیم کوتاه |
| ساخت ایمیج | روی خود سرور، با آینه‌های داخلی برای Docker و npm؛ بدون وابستگی به رجیستری خارجی هنگام اجرا |
| یک ایمیج برای api و worker | یک کد و یک build، با سه فرمان (api، worker، migrate) |
| مایگریشن | سرویس یک‌باره `migrate` که api و worker منتظر پایان موفقش می‌مانند؛ مایگریشن‌ها فقط رو به جلو هستند و پیش از هر استقرار پشتیبان گرفته می‌شود |
| پشتیبان | `pg_dump` شبانه با نگه‌داری ۷ و ۴، آزمایش خودکار بازگردانی بعد از هر پشتیبان، کپی S3 اختیاری |
| پایش | سلامت Docker، `/api/health` و `status.sh`، بدون سرویس خارجی؛ هشدار فعال بعداً (سوال ۴) |
| داده دمو | همان seed «زرین‌مدار» با رمز جدا و تازه‌سازی شبانه |
| Web Push روی سرور ایران | اگر سرویس push مرورگرها (مثلاً سرویس گوگل برای کروم اندروید) از سرور در دسترس نبود، از `PUSH_PROXY_URL` (قدم ۶ب) استفاده می‌شود. اعلان درون‌برنامه و به‌روزرسانی زنده در هر حال کار می‌کنند. این در اسکریپت دمو گفته می‌شود |

## سوال‌ها برای مالک محصول

1. **سرور و دامنه:** سرور ابری و دامنه دارید؟ کدام ارائه‌دهنده (مثلاً ابرآروان، پارس‌پک، ابردراک، هم‌روش)؟ اگر ندارید، راهنما برای خرید یک ماشین با مشخصات بالا و یک زیردامنه نوشته می‌شود. **پیشنهاد:** فعلاً راهنمای مستقل از ارائه‌دهنده و تست کامل روی ماشین آزمایشی؛ شما فقط سرور و دامنه را تهیه می‌کنید.
2. **گواهی HTTPS:** گواهی خودکار (Let's Encrypt از طریق Caddy) یا گواهی‌ای که از ارائه‌دهنده یا یک CA داخلی می‌گیرید؟ **پیشنهاد:** خودکار، با امکان گذاشتن فایل گواهی خودتان اگر از سرور در دسترس نبود.
3. **تازه‌سازی داده دمو:** هر شب خودکار (هر چه شرکت پایلوت در دمو امتحان کرده پاک می‌شود)، یا فقط با فرمان دستی پیش از هر جلسه؟ **پیشنهاد:** شبانه، تا تاریخ‌ها همیشه درست باشند و دمو همیشه تمیز.
4. **هشدار خرابی:** الان فقط وضعیت و لاگ روی سرور. اگر می‌خواهید وقتی سرویس یا پشتیبان خراب شد پیامی بگیرید، از چه راهی (پیامک، بله، ایمیل)؟ **پیشنهاد:** برای دمو لازم نیست؛ در فاز ۲ کنار سرویس پیامک اضافه شود.
