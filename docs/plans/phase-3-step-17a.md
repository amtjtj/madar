# پلن فاز ۳، قدم ۱۷الف: اصلاحیه‌های مالک محصول؛ چه کسی هدف، پروژه و کار تعریف می‌کند، زیرهدف و تقویم در خانه

> وضعیت: **پیاده‌سازی شد** · تاریخ: ۲ آبان ۱۴۰۵ · جزئیات نهایی در ADR 0027
> مرجع: درخواست مستقیم مالک محصول («اینارو اعمال کن»)؛ ADR 0005 (اجازه‌ها)، ADR 0010 (دید کارها)، ADR 0013 (هدف‌ها)، ADR 0024 (تقویم)
> قدم قبل: `docs/plans/phase-3-step-16c.md`
>
> مالک محصول خود این تغییرها را خواسته و گفته اعمال شوند، پس این پلن ثبت تصمیم‌هاست و پیاده‌سازی بدون توقف انجام می‌شود. قدم بعدی (۱۷ب) جدا پلن می‌شود و برای تایید می‌ایستد.

## هدف

- در صفحه خانه، کنار کارهای امروز، **پیش‌نمایش تقویم** هست: هفت روز پیش رو با جلسه‌ها و سررسیدها؛ با یک لمس روز را می‌بینی و با یک لمس به تقویم کامل می‌روی.
- **هدف** را فقط مدیر (رئیس یا مدیر دپارتمان) یا مدیرعامل تعریف می‌کند. کارمند هدفی را که مال اوست می‌بیند و پیشرفتش را ثبت می‌کند، ولی تعریف و نتایج کلیدی‌اش را عوض نمی‌کند.
- **پروژه** را فقط مدیر یا مدیرعامل تعریف می‌کند. هر کسی که به پروژه دسترسی دارد می‌تواند در آن کار تعریف کند و آن را به هر کسی که به همان پروژه دسترسی دارد بسپارد.
- مدیرعامل یا مدیر برای زیردستش **کار بیرون از پروژه** تعریف می‌کند؛ پروژه هم بدون این‌که زیر هدفی باشد ساخته می‌شود (مثل قبل، اتصال به نتیجه کلیدی اختیاری است).
- **هدف می‌تواند زیرهدف داشته باشد** (یا نداشته باشد): هدف شرکت زیر هدف شرکت، هدف دپارتمان زیر هدف دپارتمان، و همین‌طور تا پنج سطح.

| داخل این قدم | بیرون از این قدم |
|---|---|
| کارت «تقویم این هفته» در همه زبانه‌های خانه | ویرایش و کشیدن در خود کارت (در صفحه تقویم هست) |
| قواعد تازه ساختن هدف، پروژه و کار و سپردن کار، در API و پنهان کردن دکمه‌ها در وب (از روی اجازه‌های `/api/me`؛ endpoint تازه‌ای برای آن لازم نشد) | نقش تازه یا جدول اجازه تازه |

## ۱. قواعد

| موضوع | قاعده |
|---|---|
| **مدیرعامل** | `leadsCompany(actor)`: مدیریت همه کارها (`task.manage` در سطح شرکت، یعنی مالک) یا مدیریت هدف‌های شرکت (`goal.manage` در سطح شرکت، یعنی مالک و مدیر ارشد). بدون نقش تازه و بدون مهاجرت اجازه‌ها |
| **مدیر** | رئیس یا مدیر یک دپارتمان (`isDepartmentManager`) برای همان دپارتمان؛ و برای سپردن کار، هر کسی که در زنجیره گزارش‌دهی (`manager_id`) بالای آن شخص است |
| **هدف: ساختن** | مدیرعامل در هر سطح؛ مدیر دپارتمان برای هدف دپارتمان خودش و هدف فردی اعضای همان دپارتمان. کارمند هیچ هدفی نمی‌سازد (قبلاً هدف فردی خودش را می‌ساخت) |
| **هدف: تعریف** | عنوان، توضیح، مالک، والد، نتایج کلیدی و بایگانی: فقط مدیرعامل و مدیر همان دپارتمان (`canDefineGoal`). مالک هدف فقط پیشرفت ثبت می‌کند (`canCheckIn`) |
| **زیرهدف** | والد هم‌سطح یا بالاتر: شرکت ← شرکت؛ دپارتمان ← دپارتمان یا شرکت؛ فردی ← فردی، دپارتمان یا شرکت. همان دوره، دیده‌شدنی، فعال. هدف نمی‌تواند زیر خودش یا زیر زیرهدف خودش برود. عمق کل زنجیره حداکثر ۵ (همان سقف محاسبه پیشرفت) |
| **پروژه: ساختن** | مدیر در دپارتمان خودش؛ پروژه بدون دپارتمان فقط مدیرعامل. جابه‌جایی پروژه به دپارتمان دیگر هم همین قاعده را دارد. پروژه‌های قبلی دست نمی‌خورند |
| **کار در پروژه** | هر کسی که در پروژه کار اضافه می‌کند (`usableProjects`، مثل قبل؛ ناظر پروژه خصوصی نه) می‌تواند کار بسازد، حتی اگر عضو دپارتمان پروژه نباشد. کار در دپارتمان پروژه ثبت می‌شود (پروژه بی‌دپارتمان: دپارتمان اصلی سازنده). مسئول کار باید به همان پروژه دسترسی داشته باشد (`projectReachableBy`: صاحب یا عضو پروژه، یا دید دپارتمانی و عضو آن دپارتمان، یا دید شرکتی) |
| **کار بیرون از پروژه** | هر عضو در دپارتمان خودش کار برای خودش یا بدون مسئول می‌سازد. سپردن به **کس دیگر** فقط برای مدیرعامل، یا مدیر دپارتمانی که آن شخص عضوش است (`canAssignTo`) |
| **تغییر مسئول** | `PATCH` همان قاعده سپردن را دارد (بسته به این‌که کار در پروژه هست یا نه). برداشتن مسئول یا سپردن به خود آزاد است، مثل قبل با `canEditTask` |
| **کارهای قدیمی** | قاعده فقط برای ساختن و سپردن تازه است؛ داده موجود عوض نمی‌شود |
| **UI** | دکمه «پروژه تازه» و «هدف تازه» فقط برای کسی که اجازه دارد؛ فهرست مسئول در فرم کار فقط کسانی که می‌شود به آن‌ها سپرد (`GET /api/tasks/assignees?projectId=`). API همیشه دوباره بررسی می‌کند |

## ۲. مدل داده

بدون جدول یا ستون تازه. فقط قواعد کد و `PARENT_LEVELS` عوض می‌شود.

## ۳. API

| مسیر | تغییر |
|---|---|
| `POST /api/goals`، `PATCH /api/goals/:id` | قواعد تازه ساختن و تعریف، والد هم‌سطح، چرخه و عمق (`goal_parent_invalid`) |
| `POST/PATCH/DELETE` نتیجه کلیدی | `canDefineGoal`؛ ثبت پیشرفت `canCheckIn` |
| `GET /api/goals/:id` و فهرست | `can: { edit, checkIn }` |
| `POST /api/projects`، `PATCH /api/projects/:id` | `canCreateProject` |
| `POST /api/tasks`، `PATCH /api/tasks/:id` | قواعد کار در پروژه و سپردن (`assignee_not_allowed`) |
| `GET /api/tasks/assignees?projectId=` (تازه) | کسانی که سازنده می‌تواند کار را به آن‌ها بسپارد |

## ۴. صفحه‌ها

- **خانه:** کارت «تقویم این هفته»: هفت دکمه روز (نام روز و تاریخ شمسی با رقم فارسی و نقطه تعداد)، فهرست موارد روز انتخاب‌شده با `CalendarItemRow` (حداکثر ۵، بعد «و n مورد دیگر»)، حالت خالی و اسکلت، پیوند «تقویم کامل». داده از همان `GET /api/calendar` با لایه‌های ذخیره‌شده دستگاه.
- **هدف:** دکمه «زیرهدف تازه» در صفحه هدف (والد از پیش انتخاب‌شده)؛ والدهای هم‌سطح در فرم؛ کارمند دکمه ثبت پیشرفت را می‌بیند ولی افزودن نتیجه کلیدی و بایگانی را نه.
- **پروژه و کار:** دکمه پروژه تازه برای کارمند پنهان؛ فرم کار مسئول‌ها را از endpoint تازه می‌گیرد.

## ۵. تست‌ها

- واحد: `PARENT_LEVELS`، `leadsCompany`.
- یکپارچه (API): کارمند هدف نمی‌سازد و نتیجه کلیدی اضافه نمی‌کند ولی پیشرفت ثبت می‌کند؛ زیرهدف هم‌سطح، چرخه و عمق رد می‌شود؛ کارمند پروژه نمی‌سازد و مدیر می‌سازد؛ عضو پروژه از دپارتمان دیگر در پروژه کار می‌سازد و به عضو دیگر پروژه می‌سپارد ولی به غیرعضو نه؛ کارمند بیرون از پروژه به همکار نمی‌سپارد و مدیر به زیردست می‌سپارد؛ شرکت دیگر هیچ‌چیز نمی‌بیند.
- e2e (۳۶۰ و ۱۴۴۰): کارت تقویم در خانه؛ هدف و زیرهدف توسط مدیر و ثبت پیشرفت توسط کارمند؛ تست‌های قبلی که کارمند در آن‌ها هدف یا پروژه می‌ساخت یا به همکار کار می‌سپرد، با قاعده تازه بازنویسی می‌شوند.

## ۶. ترتیب کار

1. پلن (همین فایل).
2. shared + API: `leadsCompany`، قواعد هدف و زیرهدف، پروژه، کار و endpoint مسئول‌ها، با تست.
3. وب: کارت تقویم، دکمه‌ها و فرم‌ها، زیرهدف؛ seed و e2e.
4. ADR (افزوده به 0005 و 0013)، `CLAUDE.md`، بازبینی، push.

## تصمیم‌های من

| تصمیم | چرا |
|---|---|
| مدیرعامل = مالک یا مدیر ارشد، از روی اجازه‌های موجود | نقش تازه مهاجرت داده می‌خواهد؛ این دو نقش همان «مدیرعامل» brief هستند |
| مالک هدف پیشرفت ثبت می‌کند ولی تعریف را عوض نمی‌کند | «هدف را مدیر تعریف کند» یعنی تعریف دست مدیر است؛ ولی پیشرفت را کسی که کار را می‌کند بهتر می‌داند |
| زیردست = عضو دپارتمانی که شخص مدیرش است، یا هر کسی پایین‌تر در زنجیره گزارش‌دهی (بدون زیرمجموعه دپارتمان‌ها) | همان زنجیره‌ای که منبع کار (ADR 0017) می‌خواند؛ درخت دپارتمان در شرکت پایلوت کم‌عمق است |
| در پروژه، مسئول هر کسی که به پروژه دسترسی دارد | همان چیزی که خواسته شد؛ همکار در پروژه مشترک هنوز به همکار کار می‌سپارد |
| عمق زیرهدف ۵ | سقف موجود محاسبه پیشرفت؛ عمیق‌تر برای کاربر هم گیج‌کننده است |
